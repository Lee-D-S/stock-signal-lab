# 무료 Agent 투자팀 구성 검증

작성일: 2026-05-08

## 1. 목적

이 문서는 무료 v1 투자 Agent 시스템을 시작하기 전에, 현재 투자팀 구성이 실제 투자 프로세스에 적합한지 검증하고 각 Agent의 책임 경계를 확정하는 기준 문서다.

결론부터 말하면, 현재 v1은 **9개 Agent + 1개 orchestrator** 구조가 적합하다.

```text
QuantSignalAgent
→ StrategyDecisionAgent
→ EquityResearchAnalystAgent
→ ResearchFileAgent
→ PortfolioManagerAgent
→ RiskManagerAgent
→ ComplianceOfficerAgent
→ TraderAgent
→ OperationsReportAgent
→ FreeAgentPipeline
```

이 구조의 핵심은 “좋은 종목을 찾는 것”보다 **투자 판단을 단계별로 분리하고, 실수와 과신을 차단하는 것**이다. 무료 v1에서는 AI가 독립적으로 투자 결정을 내리는 구조가 아니라, 기존 데이터와 규칙 기반 검증을 통해 사람이 더 나은 결정을 하도록 돕는 투자 운영팀을 만든다.

## 2. 투자팀 구성 검증

현재 9개 Agent는 다음 이유로 v1에 적합하다.

| 영역 | 담당 Agent | 필요성 |
|---|---|---|
| 후보 발굴 | `QuantSignalAgent` | 감정이 아니라 데이터 기반 후보군을 만든다. |
| 전략 해석 | `StrategyDecisionAgent` | 후보 신호를 기대수익, 보유기간, 매수/감시/회피/청산 방향으로 해석한다. |
| 기업 분석 | `EquityResearchAnalystAgent` | 후보 기업의 사업, 실적, 밸류에이션, 촉매, 리스크를 분석한다. |
| 투자근거 검수 | `ResearchFileAgent` | 후보마다 리서치 근거 파일과 필수 논리 구조가 있는지 확인한다. |
| 계좌 판단 | `PortfolioManagerAgent` | 개별 종목이 아니라 전체 포트폴리오 관점에서 본다. |
| 손실 차단 | `RiskManagerAgent` | 계좌 훼손 가능성을 규칙으로 막는다. |
| 절차/기록 | `ComplianceOfficerAgent` | 근거, 기록, 금지 조건을 확인한다. |
| 주문안 | `TraderAgent` | 실제 주문 없이 검토용 주문안을 만든다. |
| 운영 기록 | `OperationsReportAgent` | 모든 판단과 경고를 보고서로 남긴다. |
| 실행 조율 | `FreeAgentPipeline` | Agent 실행 순서와 산출물 저장을 조율한다. |

이 구성은 투자회사 조직으로 보면 다음에 대응한다.

| Agent | 투자팀 내 직책 |
|---|---|
| `QuantSignalAgent` | 퀀트 리서처 |
| `StrategyDecisionAgent` | 전략 판단 리서처 |
| `EquityResearchAnalystAgent` | 기업 리서치 애널리스트 |
| `ResearchFileAgent` | 리서치 파일/품질 검수 담당 |
| `PortfolioManagerAgent` | 포트폴리오 매니저 |
| `RiskManagerAgent` | 최고 리스크 책임자 |
| `ComplianceOfficerAgent` | 준법 감시 책임자 |
| `TraderAgent` | 집행 트레이더 |
| `OperationsReportAgent` | 투자 운영/기록 담당 |
| `FreeAgentPipeline` | 투자위원회 의장 겸 운영 조율자 |

## 3. 왜 9개 Agent인가

v1에서 중요한 것은 Agent 수를 늘리는 것이 아니라, 책임 경계를 명확히 나누는 것이다.

현재 구조는 투자 프로세스의 핵심 흐름을 모두 포함한다.

```text
신호 생성
→ 전략 방향 해석
→ 기업 분석
→ 근거 확인
→ 포트폴리오 판단
→ 리스크 차단
→ 준법 차단
→ 주문안 작성
→ 기록/보고
```

이 흐름에서 빠지면 안 되는 역할은 모두 존재한다.

- Quant만 있으면 좋은 신호처럼 보이는 종목을 과신할 수 있다.
- StrategyDecision이 없으면 매수형, 반등 감시형, 회피형, 청산 감시형 후보가 같은 Candidate로 섞인다.
- Equity Research가 없으면 기업의 사업, 실적, 밸류에이션, 촉매, 리스크를 깊게 보지 못한다.
- Research File 검수가 없으면 분석 기록이 존재하는지, 오래되지 않았는지, 필수 논리가 빠지지 않았는지 확인할 수 없다.
- Portfolio가 없으면 계좌 전체 비중과 현금을 무시하게 된다.
- Risk가 없으면 한 번의 실수로 계좌가 훼손될 수 있다.
- Compliance가 없으면 투자 기록과 절차가 남지 않는다.
- Trader가 없으면 판단과 주문 입력이 섞인다.
- Operations가 없으면 사후 복기와 개선이 불가능하다.

따라서 현재 9개 Agent는 “최소이지만 충분한” v1 투자팀이다.

## 4. 각 Agent의 책임 경계

### 4.1 QuantSignalAgent

Quant는 후보를 만든다. Quant는 투자 결정을 하지 않는다.

Quant가 할 일:

- 기존 전략 신호 CSV를 읽는다.
- 후보 종목을 표준화한다.
- 점수, 조건, 신호 수, 출처를 정리한다.
- 오래된 신호나 빈 데이터는 경고한다.

Quant가 하지 말아야 할 일:

- 매수/매도 결정을 내리지 않는다.
- 리서치 근거가 있다고 가정하지 않는다.
- 리스크 한도를 통과했다고 가정하지 않는다.

### 4.2 StrategyDecisionAgent

StrategyDecision은 신호의 전략적 의미를 해석한다. StrategyDecision은 투자 승인이나 주문 실행을 하지 않는다.

StrategyDecision이 할 일:

- 후보의 `hypothesis_id`, 조건명, source_type을 전략 조건과 매칭한다.
- `action_hint`를 `buy_candidate`, `rebound_watch`, `avoid`, `exit_watch`, `hold`로 표준화한다.
- 기대수익, hit rate, 진입 규칙, 계획 보유기간을 기록한다.
- 회피/청산 감시 후보를 신규 매수 후보와 분리한다.
- 전략 해석이 오래됐거나 표본이 부족하면 경고한다.

StrategyDecision이 하지 말아야 할 일:

- 포트폴리오 비중을 판단하지 않는다.
- Risk/Compliance를 통과했다고 가정하지 않는다.
- 기대수익을 수익 보장으로 표현하지 않는다.
- 회피 후보를 매수 후보로 바꾸지 않는다.

### 4.3 EquityResearchAnalystAgent

Analyst는 기업을 분석한다. Analyst는 주문 결정을 하지 않는다.

Analyst가 할 일:

- 후보 기업의 사업모델을 정리한다.
- 실적, 재무, 밸류에이션, 수급/촉매, 리스크를 점검한다.
- 투자 가설과 반증 조건을 구조화한다.
- 기존 리서치 파일이 부족하면 보완해야 할 분석 항목을 제시한다.

Analyst가 하지 말아야 할 일:

- 실제 주문을 제안하지 않는다.
- 리스크 한도를 무시하지 않는다.
- 준법 검토 없이 확정 투자 의견을 만들지 않는다.
- 미확인 정보나 루머를 근거로 삼지 않는다.

### 4.4 ResearchFileAgent

ResearchFile은 투자 근거 파일의 존재와 품질을 점검한다. ResearchFile은 분석을 새로 쓰는 애널리스트가 아니라, 분석 기록이 남아 있는지 검수하는 역할이다.

ResearchFile이 할 일:

- 후보 종목의 리서치 파일을 찾는다.
- 리서치 파일의 최신성을 확인한다.
- 필수 섹션 존재 여부를 확인한다.
- 리서치가 부족하면 사람 검토를 요구한다.

ResearchFile이 하지 말아야 할 일:

- 없는 근거를 만들어내지 않는다.
- 리서치 파일만 있다고 자동 승인하지 않는다.
- 가격 매력이나 주문 수량을 판단하지 않는다.

### 4.5 PortfolioManagerAgent

Portfolio는 계좌 전체 관점에서 후보를 본다. Portfolio는 Risk와 Compliance를 우회하지 않는다.

Portfolio가 할 일:

- 신규 후보와 기존 보유 종목을 구분한다.
- StrategyDecision의 전략 방향과 보유기간을 참고한다.
- 현금 상태를 확인한다.
- 보유 비중과 후보 우선순위를 기록한다.
- 매수, 보유, 축소 검토 초안을 만든다.

Portfolio가 하지 말아야 할 일:

- 리스크 차단을 무시하지 않는다.
- 준법 경고를 무시하지 않는다.
- 실제 주문을 실행하지 않는다.

### 4.6 RiskManagerAgent

Risk는 손실 가능성을 차단한다. Risk는 데이터가 부족할 때 통과시키지 않는다.

Risk가 할 일:

- 주문금액 상한을 검사한다.
- 종목 비중을 검사한다.
- 섹터 비중을 검사한다.
- 일간 신규 매수 한도를 검사한다.
- 유동성 부족과 데이터 누락을 경고한다.

Risk가 하지 말아야 할 일:

- 좋은 종목이라는 이유로 한도를 완화하지 않는다.
- 포트폴리오 데이터가 없는데 승인하지 않는다.
- Compliance 판단을 대신하지 않는다.

### 4.7 ComplianceOfficerAgent

Compliance는 절차와 기록을 검사한다. Compliance는 투자 성과보다 기록의 완결성을 우선한다.

Compliance가 할 일:

- 종목코드 형식을 검사한다.
- 리서치 파일 존재 여부를 확인한다.
- 투자 근거의 필수 항목을 검사한다.
- 미확인 정보, 루머, 기록 누락을 경고한다.

Compliance가 하지 말아야 할 일:

- 법률 의견을 제공하지 않는다.
- 리서치 없는 후보를 자동 승인하지 않는다.
- Risk 판단을 대신하지 않는다.

### 4.8 TraderAgent

Trader는 주문안을 만든다. Trader는 실제 주문을 하지 않는다.

Trader가 할 일:

- Portfolio의 액션 초안을 입력으로 받는다.
- Risk와 Compliance 상태를 반영한다.
- Risk 또는 Compliance가 `approve`가 아니면 `hold`로 낮춘다.
- 현재가가 있으면 수량을 계산한다.
- 주문안 JSON을 만든다.

Trader가 하지 말아야 할 일:

- 브로커 API를 호출하지 않는다.
- `needs_review`를 매수 가능 상태로 해석하지 않는다.
- 사람 승인 없이 주문하지 않는다.

### 4.9 OperationsReportAgent

Operations는 모든 결과를 기록한다. Operations는 판단을 숨기지 않는다.

Operations가 할 일:

- Agent별 JSON 결과를 저장한다.
- 최종 Markdown 보고서를 만든다.
- 경고와 사람 확인 항목을 모은다.
- 실제 주문 금지 문구를 남긴다.
- Telegram 요약용 짧은 텍스트를 만든다.

Operations가 하지 말아야 할 일:

- 경고를 축약해서 없애지 않는다.
- 주문안을 투자 지시처럼 표현하지 않는다.
- JSON과 보고서 결론을 다르게 만들지 않는다.

### 4.10 FreeAgentPipeline

Pipeline은 투자위원회 orchestrator다. Pipeline은 개별 Agent 판단을 생략하지 않는다.

Pipeline이 할 일:

- Agent 실행 순서를 고정한다.
- 각 결과를 날짜별 JSON으로 저장한다.
- 중간에 `block`이 있어도 끝까지 보고서를 만든다.
- Portfolio, Risk, Compliance 결과를 Trader에 전달한다.

Pipeline이 하지 말아야 할 일:

- 특정 Agent 결과만 보고 전체 실행을 중단하지 않는다.
- 실제 주문 API를 연결하지 않는다.
- 경고를 무시하고 최종 승인으로 바꾸지 않는다.

## 5. Agent 간 견제 구조

이 시스템의 핵심은 각 Agent가 서로를 견제하는 것이다.

```text
QuantSignalAgent
  후보를 제안하지만, Research/Risk/Compliance가 막을 수 있다.

StrategyDecisionAgent
  후보의 전략 방향을 해석하지만, Portfolio/Risk/Compliance가 실제 매수 가능 여부를 다시 검토한다.

ResearchFileAgent
  분석 파일과 필수 논리 구조 부족을 경고하고, Compliance가 이를 절차상 문제로 다시 확인한다.

EquityResearchAnalystAgent
  기업 분석 초안을 제공하지만, Portfolio/Risk/Compliance가 매수 가능 여부를 다시 검토한다.

PortfolioManagerAgent
  매수 초안을 만들지만, Risk와 Compliance가 승인하지 않으면 Trader가 hold로 바꾼다.

RiskManagerAgent
  계좌 훼손 가능성을 차단한다. 좋은 신호라도 리스크 한도를 넘으면 막는다.

ComplianceOfficerAgent
  근거와 기록이 부족하면 매수로 넘어가지 못하게 한다.

TraderAgent
  최종 주문안 작성 단계에서 Risk/Compliance 상태를 다시 확인한다.

OperationsReportAgent
  모든 판단, 경고, 보류 이유를 사람이 볼 수 있게 남긴다.
```

가장 중요한 원칙은 다음이다.

```text
RiskManagerAgent 또는 ComplianceOfficerAgent가 approve가 아니면,
TraderAgent는 주문안을 hold로 낮춘다.
```

이 원칙은 v1 전체 시스템에서 절대 변경하지 않는다.

## 6. 전체 프로세스 검증

현재 프로세스는 투자 실무 관점에서 타당하다.

```text
1. 후보를 만든다.
2. 후보 신호가 매수형인지, 반등 감시형인지, 회피형인지, 청산 감시형인지 해석한다.
3. 후보 기업의 사업, 실적, 밸류에이션, 촉매, 리스크를 분석한다.
4. 후보의 리서치 근거 파일과 필수 논리 구조를 확인한다.
5. 계좌 전체에서 살 수 있는지 본다.
6. 손실 한도를 넘지 않는지 확인한다.
7. 절차와 기록이 충분한지 확인한다.
8. 실제 주문이 아니라 검토용 주문안을 만든다.
9. 모든 결과를 보고서로 남긴다.
```

이 순서가 중요한 이유는 다음과 같다.

- Analyst보다 Quant가 먼저인 이유: 후보가 있어야 기업 분석 대상을 정할 수 있다.
- StrategyDecision이 Quant 뒤에 있는 이유: 후보가 어떤 전략 행동인지 먼저 분리해야 Portfolio가 신규 매수와 회피/청산 감시를 혼동하지 않는다.
- ResearchFile이 Analyst 뒤에 있는 이유: 분석 결과와 기존 리서치 파일의 기록 품질을 따로 검수해야 한다.
- Portfolio가 Risk보다 먼저인 이유: 제안 금액과 액션 초안이 있어야 리스크 검사가 가능하다.
- Risk와 Compliance가 Trader보다 먼저인 이유: 주문안은 차단 결과를 반영해야 한다.
- Operations가 마지막인 이유: 모든 Agent 결과를 모아야 최종 회의록이 된다.

## 7. v1에서 추가 Agent를 만들지 않는 이유

장기적으로는 다음 Agent가 유용하다.

- `DataQualityAgent`
- `MacroRegimeAgent`
- `PerformanceReviewAgent`

하지만 v1에서는 별도 Agent로 만들지 않는다.

이유:

- Agent 수가 늘면 운영 복잡도가 증가한다.
- 현재 핵심 목표는 실제 주문 없는 안전한 검토 파이프라인 구축이다.
- 데이터 품질은 Quant와 Risk에서 일부 처리할 수 있다.
- 시장 국면은 v1에서 필수 차단 Gate가 아니다.
- 성과 리뷰는 주문 실행 이후 중요해지므로 v1 후순위다.

따라서 v1에서는 9개 Agent를 먼저 신뢰 가능하게 만든다.

향후 확장 기준:

| 후보 Agent | 분리 시점 |
|---|---|
| `DataQualityAgent` | 데이터 누락/오류가 투자 판단의 주요 병목이 될 때 |
| `MacroRegimeAgent` | 시장 국면에 따라 전략 노출을 조절해야 할 때 |
| `PerformanceReviewAgent` | 실제 매매 기록이 누적되어 전략별 성과 평가가 필요할 때 |

## 8. 무료 v1 자동화 경계

무료 v1에서 자동화할 수 있는 것:

- 후보 종목 정리
- 기존 신호 CSV 해석
- 기업 분석 체크리스트 생성
- 리서치 파일 존재 여부 확인
- 리스크 한도 검사
- 준법 체크리스트 검사
- 주문안 JSON 생성
- 최종 보고서 생성

무료 v1에서 자동화하면 안 되는 것:

- 실제 주문 실행
- 사람 승인 없는 매수/매도
- 유료 LLM API 기반 투자 판단
- 타인 자금 운용
- 투자자문/투자일임 행위
- 법률/세무 판단
- 미확인 정보 기반 매매

## 9. 성공 기준

이 투자팀 구성은 다음 조건을 만족해야 성공이다.

- OpenAI API 키 없이 실행된다.
- 브로커 주문 API를 호출하지 않는다.
- 후보가 없어도 보고서가 생성된다.
- 기업 분석이 부족하면 사람 검토 항목으로 남긴다.
- 리서치가 없으면 자동 승인하지 않는다.
- 포트폴리오 데이터가 없으면 매수 판단을 보류한다.
- Risk 또는 Compliance가 `approve`가 아니면 Trader는 `hold`를 만든다.
- 모든 Agent 결과가 JSON으로 남는다.
- 최종 보고서만 봐도 어떤 후보가 왜 막혔는지 알 수 있다.

## 10. 기본 운영 원칙

최종 운영 원칙은 다음으로 고정한다.

```text
1. 신호는 제안일 뿐이다.
2. 기업 분석 없는 신호는 투자 근거가 아니다.
3. 리서치 파일 없는 분석은 기록으로 부족하다.
4. 포트폴리오 없는 매수 판단은 불완전하다.
5. 리스크 한도는 좋은 종목에도 적용된다.
6. 준법 경고는 수익 기회보다 우선한다.
7. Trader는 주문하지 않고 주문안만 만든다.
8. 모든 판단은 기록으로 남긴다.
9. 사람 승인 전에는 어떤 주문도 실행하지 않는다.
```

## 11. Test Plan

이 문서가 기준 문서로 충분한지 다음 항목으로 검증한다.

- 9개 Agent의 책임이 서로 겹치지 않는지 확인한다.
- StrategyDecisionAgent가 Quant와 Portfolio 사이의 책임 공백을 메우는지 확인한다.
- 각 Agent가 하지 말아야 할 일이 명확한지 확인한다.
- Risk와 Compliance의 독립 Gate 역할이 명확한지 확인한다.
- Trader가 실제 주문을 하지 않는다는 원칙이 명확한지 확인한다.
- 추가 Agent를 v1에서 제외하는 이유가 설명되어 있는지 확인한다.
- 이후 Agent별 상세 PLAN이 이 문서를 기준으로 작성될 수 있는지 확인한다.

## 12. Assumptions

- v1은 9개 Agent와 `FreeAgentPipeline`을 목표 구조로 삼는다.
- 추가 Agent는 이번 단계에서 구현 대상으로 삼지 않는다.
- 실제 주문 자동화는 범위에서 제외한다.
- 무료 버전은 외부 유료 LLM API를 사용하지 않는다.
- 사람의 최종 승인이 투자 결정의 마지막 단계다.
